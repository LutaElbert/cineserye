# Cineserye agent specification

## Overview

Cineserye's first agent workflow turns one creator-selected scene into a cited, budget-aware, chronological shot proposal. A coordinator runs a research phase backed by Parallel, then a shot-planning phase backed by Gemini on Vertex AI. The result is normalized into Cineserye cinema-domain records and compiled through the existing validated canvas-command boundary. The agents cannot write directly to the canvas, IndexedDB, backups, or exports.

The prototype runs locally. It uses the existing TypeScript React/vinext repository, ADK for TypeScript where agent primitives add value, and Google Agents CLI for workspace development guidance, local debugging, evaluations, traces, and telemetry. It does not deploy an agent or introduce a Python production service.

## Architecture and approaches considered

### Selected: sequential coordinator with two specialist phases

```text
Scene Planning Coordinator
  ├── Research phase
  │     └── Parallel research tool
  └── Shot Planning phase
        └── Vertex Gemini structured output

Validated cinema result
  → CanvasCommandProposal compiler
  → ghost review
  → explicit accept or reject
```

The workflow is sequential because research must be available before shot planning. The coordinator owns lifecycle state and cancellation; deterministic TypeScript code owns runtime validation, cost checks, and command compilation.

### Rejected: one free-form agent with every tool

This is smaller initially but makes tool trajectories, citation provenance, repair behavior, and evaluation harder to isolate.

### Rejected: Agents CLI Python scaffold as the production runtime

The installed Agents CLI coding reference is Python-focused. Adding a Python service would create a second production stack and conflict with the approved TypeScript architecture. Agents CLI may still evaluate or trace a compatible local endpoint.

## Example use cases

### One-location period suspense scene

**Input:** A selected scene set in a late-1980s Manila cinema; restrained supernatural suspense; micro-budget band; ₱1,200 ceiling; 36-second target.

**Expected output:** Three to eight chronological shots, separate storyboard and video prompts, Mara/location/prop continuity dependencies, cited material-culture and cinematography findings, and a minimum/expected/high-risk generation-cost range.

### Dialogue-led contemporary scene

**Input:** A selected two-character scene; intimate tone; contemporary interior; low-budget band; phone camera and one practical light.

**Expected output:** A coverage-efficient shot proposal that respects equipment and duration constraints without inventing unnecessary locations or props.

### Limited research result

**Input:** A valid scene whose Parallel queries return few usable sources.

**Expected output:** A conservative proposal marked `limited-research`, with no unsupported citations and clear retry guidance.

## Tools required

### Parallel research tool

- **Purpose:** Research location/period authenticity, props and material culture, cinematography references, and vertical-format staging.
- **Authentication:** Server-only `PARALLEL_API_KEY` environment variable.
- **Output:** Normalized sources containing stable ID, title, publisher, URL, finding, query purpose, retrieval time, and status.
- **Limits:** Bounded query count, timeout, cancellation, deduplication, supported URL protocols, and result-count caps.

### Vertex Gemini planner

- **Purpose:** Convert the scene brief and normalized research into schema-constrained cinema-domain output.
- **Authentication:** Google Application Default Credentials for account `elbertluta@gmail.com`, quota project `cineserye`.
- **Project:** `cineserye`.
- **Location:** `global` unless a required model or organization policy demands a supported regional location.
- **Model:** `gemini-3.7-flash`, confirmed available to the project on 2026-09-01.
- **Limits:** One bounded structural repair attempt; no direct editor commands or autonomous acceptance.

### Cineserye validation and command compiler

- **Purpose:** Validate domain relationships, continuity, duration, costs, source references, and the final canvas proposal.
- **Authentication:** None.
- **Output:** A cloned, validated `CanvasCommandProposal` result suitable for ghost preview.
- **Limits:** Existing graph, lock, batch-size, node-kind, and command restrictions remain authoritative.

## Data flow and state

1. The browser submits a validated scene brief to a server-only endpoint.
2. The endpoint creates an `agent-run` with a unique `run_id`.
3. The research phase calls Parallel and returns normalized sources.
4. The planning phase sends only the required scene constraints and normalized research to Vertex Gemini.
5. Runtime validators reject or repair malformed planner output.
6. Deterministic code calculates cost ranges and compiles canvas commands.
7. The browser receives a ready proposal and cinema sidecar; the saved document remains unchanged.
8. The creator accepts or rejects the complete proposal. Acceptance is one undoable history entry.

Run lifecycle:

```text
draft → researching → planning → validating → ready
  └──────────────→ failed | cancelled
ready → accepted | rejected
```

No cross-session personal memory is required. Ready and accepted run records persist as project data, not agent memory.

## Constraints and safety rules

- Never expose Parallel keys, Google credentials, access tokens, request headers, or raw provider configuration to the browser.
- Never allow an LLM or tool to import or invoke editor mutation, persistence, backup, or export functions.
- Treat every provider response as untrusted and validate it at runtime.
- Never mutate the saved canvas before explicit user acceptance.
- Never deploy, publish, enable cloud telemetry, or create infrastructure without separate approval.
- Record no raw scene text, complete prompt, raw citation body, credential, or provider response in default telemetry.
- Reject unresolved scene, shot, character, asset, prompt, source, or command references.
- Bound scene length, sources, shots, prompts, commands, retries, and provider timeouts.
- Preserve the generic editor and its accessibility, persistence, graph, backup, and undo behavior.
- Label generation costs as illustrative rather than guaranteed production prices.
- A failure, timeout, cancellation, or rejection creates no canvas history entry.

## Edge cases to handle

- Empty or excessively long scene text.
- Missing tone, location/period, or budget.
- Parallel returns zero results, duplicate URLs, malformed URLs, a rate limit, or a timeout.
- Vertex returns invalid JSON, unknown enum values, duplicate shot numbers, unresolved dependencies, or durations outside tolerance.
- Proposed high-risk cost exceeds the user ceiling.
- The selected scene is deleted or changed while a run is active.
- The browser reloads with a ready proposal.
- A second run is requested while one is active for the same scene.
- The user rejects, accepts, undoes, or redoes a proposal.

## Success criteria

- 100% of ready proposals pass cinema-domain and canvas-command runtime validation.
- A valid fixture scene produces three to eight chronological shots.
- Summed shot duration stays within ±10% of the requested target.
- Every shot has one storyboard prompt, one video prompt, a production purpose, and resolved continuity dependencies.
- 100% of displayed research-backed claims resolve to a normalized source URL.
- Cost ranges always satisfy `minimum ≤ expected ≤ high-risk`, and totals reconcile with shot estimates.
- Preview and rejection leave the source document byte-equivalent.
- Acceptance creates exactly one history entry; one undo reverses the complete proposal.
- Fixture mode produces no external network requests.
- No serious or critical automated accessibility violations occur in brief, planning, review, and accepted states.
- Evaluation cases record dataset version, agent version, model/provider configuration, trace ID, and scoring policy.
- Default traces contain no raw scene fixture, complete prompt, API key, access token, or raw provider response.

## Evaluation and telemetry

Initial deterministic cases:

1. The Reel That Knows Tomorrow — period suspense, one location, ₱1,200 ceiling.
2. Dialogue-led contemporary scene — two characters, minimal coverage, constrained equipment.
3. Genre-contrasting scene — verifies that tone follows user intent rather than a fixed product genre.

Initial metrics: schema validity, citation coverage, continuity completeness, duration reconciliation, budget compliance, production usefulness, and mutation safety.

Trace hierarchy:

```text
cineserye.agent_run
  ├── research.parallel
  ├── planning.vertex
  ├── validation.cinema_domain
  ├── proposal.canvas_commands
  └── review.accept | review.reject
```

Cloud trace export is opt-in. Fixture and ordinary pull-request tests retain sanitized telemetry locally.

## Assumptions

- The Parallel API key is not yet configured; live Parallel testing waits for a server-only key.
- Google ADC remains local and uses the `cineserye` quota project.
- The first implementation uses a deterministic sequential workflow; A2A is unnecessary.
- The first implementation is local-only and uses fixture mode in automated tests.
- Storyboard prompts are text artifacts; no images or videos are generated.
